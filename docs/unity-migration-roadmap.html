00 · Decisiones canónicas

Primero conservar. Después transformar.

La migración no es una reescritura creativa. Es una operación de paridad con puertas de salida medibles y una sola fuente de verdad durante cada etapa.

Decisión 01 Unity 6.3 LTS

Versión fijada para producción; no se persigue cada Update durante el port.

Decisión 02 Paridad funcional

Fórmulas, contenido, probabilidades y flujo preceden cualquier mejora de UX.

Decisión 03 Monorepo temporal

El proyecto nace en unity/; la versión web sigue siendo el oráculo ejecutable.

Decisión 04 Gemini fuera del runtime

La IA queda como herramienta de autoría; el build solo consume assets aprobados.

Regla de corte

Una fase no termina cuando “se ve bien”, sino cuando su salida reproduce el mismo resultado con los mismos datos y una semilla conocida. Las diferencias intencionales requieren un registro de decisión antes de entrar en Unity.

Dentro de v1

  • Campaña completa y torre infinita.
  • Combate manual, IA enemiga, simulación y balance.
  • Exploración Region → Location → 10 Room.
  • Todos los jutsus, eventos, enemigos, objetos y assets aprobados.
  • Teclado y ratón en Windows.

Fuera de v1

  • Móvil, WebGL, consolas y soporte completo de gamepad.
  • Nuevas mecánicas, regiones o rediseño de progresión.
  • Multijugador, telemetría remota y servicios live.
  • Generación de imágenes o secretos de API dentro del cliente.
  • Guardado de run como nueva feature; solo paridad de metaprogreso.

02 · Arquitectura destino

Unity en el borde. El juego en el centro.

La lógica portada conserva la separación actual: matemáticas y reglas puras, orquestación explícita, contenido inyectado y presentación reemplazable.

Assembly 01

ShinobiWay.Domain

Enums, DTOs, value objects y contratos. Cero referencias a UnityEngine, UI, archivos o reloj del sistema.

Assembly 02

ShinobiWay.Gameplay

Fórmulas, combate, IA, deck, loot, eventos, exploración y progresión. Funciones deterministas sobre Domain.

Assembly 03

ShinobiWay.Application

Máquina de estados, comandos de jugador, sesión, casos de uso y adaptadores para contenido, guardado, RNG y logging.

Assembly 04

ShinobiWay.Presentation

UI Toolkit, presenters, Input System, cámara 2D, audio, VFX y carga de escenas. Nunca contiene fórmulas de balance.

Assembly 05

ShinobiWay.Content.Editor

Importadores, validadores, generación de catálogos, Addressables y utilidades de autoría. No entra en el player.

Dirección permitida Presentation→ Application→ Gameplay→ Domain

Origen web Destino Unity Regla de migración
src/game/types.ts Domain · enums y DTOs C# Conservar nombres, valores serializados e IDs; documentar cualquier valor legacy.
src/game/systems/ Gameplay · servicios puros Portar por dependencia, sin MonoBehaviour, coroutines, Time ni acceso a assets.
App.tsx + hooks Application · comandos y controladores Extraer coordinación; ninguna traducción uno-a-uno de hooks a componentes Unity.
GameState + scene registry GameFlowState + router Una transición pasa por guardas tipadas y declara su payload requerido.
React + CSS UXML + USS + presenters UI Toolkit para HUD, menús y overlays; sprites 2D para el escenario de combate.
Constantes TypeScript JSON intermedio + ScriptableObjects Generación repetible, IDs estables y validación; nunca doble autoría manual.
localStorage ISaveRepository + JSON local En v1 persiste metaprogreso equivalente; no añade reanudación completa de run.
Logs de UI y consola ShinobiWay.Diagnostics Sinks aislados; Domain y Gameplay emiten datos, no llaman a Debug.Log.

05 · Cadena de contenido

Una sola verdad. Cinco estaciones.

Durante la coexistencia, TypeScript sigue siendo canónico. Unity nunca se autoriza a mano en paralelo: recibe una exportación verificable hasta el corte final.

01 · Autoría TypeScript

Constantes actuales, IDs estables y manifests son la verdad mientras la web sea el oráculo.

02 · Normalización JSON generado

Un script Node materializa datos puros, enumera referencias y rechaza contenido no serializable.

03 · Validación Schema + enlaces

Se verifican duplicados, IDs ausentes, ciclos inválidos, rutas de arte y campos fuera de rango.

04 · Importación ScriptableObjects

El importador actualiza assets idempotentes y conserva GUIDs para no romper escenas ni Addressables.

05 · Runtime Repositorio

IGameContentRepository sirve definiciones inmutables sin conocer AssetDatabase.

Cambio de autoridad en el cutover

Cuando Unity apruebe la matriz completa, el JSON normalizado pasa a ser fuente canónica. Las constantes web quedan congeladas; el exportador de transición se archiva después de una release estable, no antes.

07 · Definición de final

Cómo se demuestra el relevo.

El corte solo es válido cuando reglas, contenido, recorrido y build se sostienen juntos. Ninguna captura bonita sustituye estas evidencias.

Evidencia A

Paridad de reglas

  • Fixtures críticos equivalentes con semillas fijadas.
  • Sin diferencias no registradas en fórmulas o probabilidades.
  • Simulación dentro de win rate 45–65% y TTK 4–12 cuando aplique.
  • Cero llamadas Unity desde Domain o Gameplay.
Evidencia B

Paridad de producto

  • 116 jutsus, 43 eventos y 4 regiones validados.
  • Campaña y Infinite Tower completables.
  • Todas las actividades y estados alcanzables sin soft-lock.
  • Feedback visual conserva legibilidad y dirección artística.
Evidencia C

Preparación de release

  • Build Windows reproducible desde una máquina limpia.
  • 60 FPS a 1080p y memoria estable en hardware objetivo.
  • Sin excepciones en soak de campaña y torre.
  • Rollback, licencias, versión y fuente canónica documentados.
