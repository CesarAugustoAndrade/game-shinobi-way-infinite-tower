## Génesis

**Why this gap:** SOUL §8 family rules and §16 acceptance require two distinct same-family transitions:

| Transition | Economics | Charges | Prior Mode |
|------------|-----------|---------|------------|
| **Ascenso** (Gate/Curse superior) | Full AP of target + **activation resource diff** | remaining **+1** (cap new max) | Becomes new stage (no dual ON) |
| **Lateral** (Sharingan 2T↔3T) | **Full** activation of target | Transfer **without** refill/+1 | Prior → **COOLDOWN** |

Canon: [`docs/combat-tactical-setup-spec.html#modes`](../../docs/combat-tactical-setup-spec.html#modes), SOUL §8 family table, §16 “Ascenso Gate/Curse” / “Sharingan lateral”, §3.4 Modes.

**Code evidence:**

## Context

Mode machine and skill packaging exist. Playing a higher-stage Gate/Curse Mode card while the lower stage is ON either fails `same-family` or, if the caller forces `family-replace`, applies **lateral** economics (full cost, no +1 charge, prior CD) which contradicts SOUL ascenso. Sharingan lateral is only reachable via explicit `modeOp` + `replaceTo`. This task makes pure `resolveSkill` choose and apply the correct T-005 transition from SOUL family rules when a MODE skill targets a different stage of an already-ON family.

## Spec

### Must exist when done

1. **Family transition classifier (pure)**  
   Given board + target `ModeDefinition` (from skill `modeInteraction.modeId` / `getModeDefinition`):
   - Find ON instance with **same `family`** and **different `id`** (if any).
   - If none → normal **activate** (existing).
   - If same id already ON → existing **already-on** / manual-off path (no invent).
   - If same family, target `stage` **>** current `stage`:
     - Family **GATES** or **CURSE** → **ascent** (`ascendMode`).
     - Family **SHARINGAN** → **lateral** (`lateralSwap`).
   - If target stage **≤** current → reject (no downgrade); do not invent soft swap.
   - Document the rule in a one-line comment on the helper (SOUL §8).

2. **`resolveSkill` MODE auto-route**  
   - When `modeOp` is omitted / `'activate'` and classifier says ascent or lateral: run that transition with `replaceTo` = target def (caller may still pass explicit `modeOp: 'family-replace'` + `replaceTo`).
   - Explicit `modeOp: 'family-replace'` must use the **same classifier** (not hardcode lateral) so Gate/Curse never get lateral by default.
   - Prefer injecting `ports.ascendMode` / keep `familyReplace` as the chosen op, or a single `ports.familyTransition` — keep immutability and testability.
   - On failed transition (cannot afford, not-on, not-ascent): **consume nothing** if failure is detected in validate; if post-commit failure remains for edge cases, prefer validate-first so AC1/AC2 see clean reject (align T-007 invalid = no consume).

3. **Observable economics (fixtures use real defs from `modes.ts`)**  
   - **Ascenso Curse I→II (or Gate Life→Limit):** after success, only higher stage ON; charges = `min(maxCharges, priorCharges + 1)`; pools paid per `ascendMode` (AP = target activation AP; HP/CP = diff only) **without double-paying full lower+upper activation**. If skill pre-commit currently double-taxes Mode activates, fix **this path** so SOUL ascent numbers match T-005 unit expectations (document any shared helper with plain activate if touched).
   - **Lateral Sharingan 2→3:** charges transferred (no +1); `sharingan_2` COOLDOWN; `sharingan_3` ON; full target activation resources per `lateralSwap`.
