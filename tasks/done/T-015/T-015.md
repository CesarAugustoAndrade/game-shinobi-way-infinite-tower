## Spec

### Must exist when done

1. **Author SOUL Mode weightModifiers (data)**
   - At minimum **required** SOUL explicit route:
     - `shadow_clone` (CLONES): `{ skillId: 'rasengan', delta: 4 }` (or project-stable Rasengan id if different — must resolve to catalog Rasengan skill id).
   - **Optional but preferred** if SOUL/HTML notes already name a clear skill/role delta without inventing numbers (use only deltas stated in SOUL text or existing enhancement notes that quote a number):
     - Do **not** invent Gate Prep +3 unless that Mode/support is in scope as a skill row (Gate Prep is a Support in §11, not a Mode row) — **out of scope** for inventing.
   - Empty arrays on Modes with no SOUL-stated skill weight delta remain OK.

2. **Pure aggregator**
   - `buildModeWeightBonuses(activeModes, getModeDefinition?) → Readonly<Record<string, number>>`:
     - Consider only Modes in **ON** (or project-equivalent active) state.
     - Sum `delta` per target `skillId` from each ON Mode’s `weightModifiers`.
     - Tag/role modifiers: if `WeightModifier` has `tag`/`role` without `skillId`, apply only when a **provided skill list** is passed (optional second form) — **minimum AC is skillId path**; tag/role may be deferred if unused by authored rows.
   - No `Math.random`; pure and immutable.

3. **Draw integration (pure / call-site)**
   - Documented API: callers pass `modeBonuses: buildModeWeightBonuses(...)` into `drawHand` / `drawNewTurnHand` weight context.
   - If `processUpkeep` already has access to `combatState.activeModes` (or will after T-012), wire the builder there **when modes present**; if not yet on live path, export helper + unit tests suffice for AC, with a one-line call-site where pool+modes are both available without inventing Mode board.

4. **Transparency**
   - Rasengan with Shadow Clones ON must have **strictly higher** `effectiveWeight` than same Rasengan with clones OFF (same posture, no CD), by **exactly +4** from the Mode term (base/posture held fixed).
